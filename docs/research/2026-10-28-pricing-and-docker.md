# Pricing a private Scry box: the call brief

Research for Trey and Wes · 28 October 2026

**Reading note.** All linked external sources in this report were read on 2026-10-28. Public list prices can change; taxes, promotions and currency conversions are not included. A virtual private server (VPS) is a virtual computer running on a provider's physical server; “one box per group” here means one VPS and disk per group, not a dedicated physical machine. The companion [box-provider report](2026-10-28-box-providers.md) is the source for prior provider and bandwidth research; do not read the illustrative capacities below as tested Scry performance.

## One-page call brief

**Pricing:** Test **$30 per group per month**, not per person, with **$300 paid annually** as a proposed early-customer offer. The annual price averages $25/month, not $30; its discount buys a year of commitment but leaves little headroom at the starting-box cost. For a cheaper option, test a $25/month small-group plan only if a smaller VPS survives real calls and leaves adequate margin. Do not sell a 50-person concurrency promise until tested. Prices are proposed, not market validation. A 14-day money-back period is a proposed customer-friendly alternative to provisioning an unrestricted free box; its abuse and refund costs remain unmodeled.

**The arithmetic:** Use the prior report's DigitalOcean 2-vCPU/2-GiB VPS at $18 plus a separate 20-GiB disk at $2, and assume **$1/month for encrypted backups solely as a placeholder**, not a verified quote. US domestic online card processing is **2.9% + $0.30 per successful transaction** ([Stripe](https://stripe.com/pricing)); if using Stripe Billing for subscriptions, its pay-as-you-go charge adds **0.7% of Billing volume** ([Stripe Billing](https://stripe.com/billing/pricing)); both read 2026-10-28. The table includes both, assumes one monthly charge, and excludes taxes, support, chargebacks, network overage, failed payments and provisioning costs. Amounts rounded to cents; negative means we lose money before all those excluded costs.

**Providers:** DigitalOcean is the most practical first build because Scry's existing deployment path is designed around it; Lightsail's $12 bundle is an attractive cost experiment but counts inbound and outbound against its allowance; Vultr's $15 bundle is another experiment, but price the exact attached disk before quoting. **Docker verdict, in three sentences.** Docker on the same VPS is packaging, not cheaper infrastructure, and explicitly changes Wes's rule 5. It can make publishing reproducible images and reaching home-box app stores easier, but adds an engine, image-verification, firewall and maintenance surface; locked-at-boot storage is possible only if deliberately built and tested on the host. Shared-container panels and managed container platforms are different trust and isolation models, not a free substitute for one customer VPS.

**How to phrase a limit.** Offer a published included monthly outbound-transfer allowance appropriate to the chosen provider, visible usage and warning before the threshold, and a conversation/upgrade before recurring heavy usage; specify whether resets and pooled provider allowances are per customer. Do not call it “unlimited” if a cap, throttle, or discretionary cutoff applies. At the earlier report's stated assumptions, ten people all sending video use roughly 40.5 GB outbound per hour, so a nominal 1 TB lasts about 25 such hours before other traffic; this is an example, not a Scry measurement ([prior report](2026-10-28-box-providers.md)). A hard cap risks silently killing a call; choose a visible, humane enforcement policy before selling.

### DNS for customer subdomains

DNS maps a name to an IP; authoritative DNS need not proxy the application's traffic. One Scry-owned zone with one record per group avoids buying one zone per customer. Read 2026-10-28: [DigitalOcean DNS](https://docs.digitalocean.com/products/networking/dns/details/pricing/) free; [Vultr DNS](https://www.vultr.com/api/) has record API and free DNS advertised; [deSEC](https://desec.readthedocs.io/en/latest/rate-limits.html) free, but rate-limited and requires its DNSSEC/delegation terms; [Porkbun](https://porkbun.com/llms/dns) free DNS for its registered domains, subject to API access and account restrictions; [Route 53](https://aws.amazon.com/route53/pricing/) $0.50/zone/month for the first 25 zones plus queries; [Bunny](https://bunny.net/blog/were-making-bunny-dns-free/) free DNS with a $1/month account minimum; [Hetzner DNS](https://www.hetzner.com/dns/) free, with zone limits. API suitability, renewal and abuse limits still need a provisioning test. Do not enable Bunny's CDN or proxy. Cloudflare proxy is banned by rule 1; GAMEPLAN §2 says DNS-only is permissible, but the brief treats it as a gray area, so **do not recommend it without Wes's explicit approval**.

## 3. Docker as a real alternative

### 3a. Same machine, different packaging

On one VPS per group, a plausible Compose manifest describes the app, Postgres, LiveKit, nginx and a scheduled restic backup task. Image versions should be pinned by immutable digest; secrets and database files stay on the encrypted host volume, mounted into the right containers. Docker Compose is not itself a provisioner for customer billing, a secure unlock flow, firewall policy, or tested backups. Use systemd on the host to sequence unlock, mount and Compose; automatic container restart must not start anything against an empty fallback directory before the LUKS mount exists. Restic secrets, caches, persistent logs, database data and runtime secrets must also remain on the encrypted volume, as required by [GAMEPLAN.md §1b](../../GAMEPLAN.md). No passphrase is persisted on the box. An authenticated remote unlock, TLS bootstrap, restore and reboot behavior still need design and end-to-end tests.

GAMEPLAN §2b says bonesdeploy uses per-site Linux users, systemd, AppArmor and cgroups, “without a root daemon, an image registry or a container runtime in the trust chain.” Docker [confirms](https://docs.docker.com/engine/security/) its daemon normally requires root unless rootless mode is chosen; rootless changes the privilege model but does not make rule 5's no-Docker requirement disappear. Docker [warns](https://docs.docker.com/engine/network/packet-filtering-firewalls/) published container ports can bypass UFW rules; test the actual firewall from outside, rather than assuming the existing policy applies.

[LiveKit's docs](https://docs.livekit.io/transport/self-hosting/deployment/) recommend host networking for Docker performance; its [port reference](https://docs.livekit.io/transport/self-hosting/ports-firewall/) specifies the default 50000–60000/UDP range and also offers an optional single UDP mux port. Host networking reduces network isolation; mapped ports require verified public address advertisement and TURN fallback. Treat a mux as a potential implementation choice, not proof every client and TURN scenario works; test real networks and the Scry-specific config. LiveKit's recommendation of a proxy for HTTPS need not mean a third party: nginx on the same customer VM is compatible with the current traffic boundary.

For image trust, Wes or a delegated release signer could sign image digests with a protected key held off the box; the installer must verify the intended signer and digest *before* starting. [Sigstore Cosign](https://docs.sigstore.dev/cosign/signing/signing_with_containers/) documents local-key signing and registry signatures. Docker says its [Docker Content Trust / Notary v1 service](https://docs.docker.com/retired/) shuts down on 8 December 2026, so do not build a new dependency on it. Signatures authenticate a publisher, not the absence of vulnerabilities; verify base images and rebuild deliberately. Docker's [release notes](https://docs.docker.com/engine/release-notes/) show repeated security and maintenance releases, not a fixed monthly update promise. Docker daemon and image memory/disk overhead on this stack are **unmeasured**; benchmark on the target machine, especially with swap disabled.

**Panel and billing are separate products.** [Pelican](https://pelican.dev/) is an open-source game-server control panel backed by Docker containers; [Paymenter](https://github.com/Paymenter/Paymenter) is an open-source hosting billing platform. A customer-facing panel can provide lifecycle controls and console; actual backup functionality, Scry-specific setup, provisioning hooks, Stripe checkout, cancellation/export and owner unlock need integration and testing, not an assumption that both projects solve them together. The researcher found Paymenter's built-in integration for Pterodactyl, not Pelican; third-party Pelican extensions exist but compatibility and real Wings-node behavior are **unconfirmed**. There is a root-capable Docker control plane, shared kernel and potentially shared node. An E2EE media key still need not reach the host, but the host can inspect the unlocked filesystem and any server-readable data, and a compromised web-served client can be poisoned. Many LiveKit instances require distinct address/port assignments; multiplexing may reduce the port burden but is not a proven solution to TURN, address advertisement and isolation. This is a different product from a VPS per group, not a shortcut that preserves the promise.

**Home stores: more distribution, not automatic acceptance or revenue.** These channels are for the self-hosted door, not evidence of paid-hosting demand. Listing value, audience conversion and any fees are **unconfirmed**.

## What I could not confirm

* Real Scry concurrency, per-group memory, transfer, support and backup costs; no VPS, container, encrypted reboot or restore was tested in this research.
* Account-specific Stripe fees, tax, card-dispute and international-card costs; the illustrative margin is not a complete profit estimate.
* Every unconfirmed field in the provider, platform and app-store tables, and providers' written approval for the precise Scry resale model.
* The actual secure per-owner unlock, recovery, TLS bootstrap and operation of a multi-customer system without weakening rules 1, 5, 8 or 9.
