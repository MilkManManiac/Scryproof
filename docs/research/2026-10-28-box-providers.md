## 1. How provisioning works and who can do it

A **cloud-init** file is a first-boot script supplied when creating a VM. **Block storage** is an additional raw disk the operating system can format; Scry can put LUKS, Linux's disk encryption, on it. A **firewall** limits which network ports accept traffic. **DNS** maps a name to an address; ordinary authoritative DNS answers are not a traffic proxy. **Reverse DNS** maps the address back to a name and is not generally necessary for web/voice service. TLS encrypts the connection to a site's web server.

### A builder's first flow

1. Accept a paid Stripe event, verify its signature, and deduplicate by event and subscription ID. Record a provisioning job and selected region. Do not trust the browser redirect as proof of payment. Apply fraud checks and a quota before buying anything.
2. Reserve a unique customer hostname; ensure its DNS zone is hosted by a DNS provider with a write API. Use a narrow-scope DNS token. The group may later point a domain they own, but that is a separate setup flow.
3. Create an Ubuntu VM through the provider API with a restricted SSH key, a unique non-secret job identifier, and cloud-init referencing a versioned, integrity-checked installer. Never put a disk passphrase, API keys, backup password, private key, or long-lived credential in cloud-init, provider metadata, shell logs, root filesystem, or a process argument. DigitalOcean documents that user-data is supplied at creation and logged during execution ([cloud-init](https://docs.digitalocean.com/products/droplets/how-to/provide-user-data/)). A cloud host can inspect the machine while it runs; LUKS primarily protects a powered-off disk, not against a malicious host or root access to an unlocked box.
4. Create a separate unformatted disk in the same region and attach it. Wait until its exact device identity is confirmed, and run a one-time initialization that **refuses to format a device already containing data**. Do not race the installer against disk attachment; first-boot may finish earlier. A partition or encrypted file on the boot disk could instead avoid a separate disk charge, but it changes failure/restore and resizing assumptions and is not proven compatible with today's install.
5. Create firewall rules via API. For the LiveKit example, the upstream guide lists 80/TCP, 443/TCP, 7881/TCP, 3478/UDP and 50000–60000/UDP; align with Scry's *actual* configuration, including TURN/TLS sharing or port conflicts and restricted administration, rather than copying that Docker-based guide blindly ([LiveKit VM guide](https://docs.livekit.io/transport/self-hosting/vm/)).
6. Create DNS A/AAAA records to the actual public address, wait for resolution and issue a certificate. Run a minimal unlock service and nginx on the unencrypted root with no application secrets. An unlock page cannot depend on the encrypted Scry application, a private key stored on the volume, or a certificate issuance process that requires an inaccessible service. Decide where the web TLS private key lives: storing it unencrypted conflicts with “nothing secret on root.” The unlock-page trust/bootstrap mechanism is a **design blocker**, not something to paper over.
7. Send the owner an authenticated setup link via a trusted channel. The owner supplies or creates the passphrase directly to the box over a verified secure connection; initialize/unlock LUKS without recording it in provider metadata, web logs, analytics, or the control plane. Once mounted, start Postgres, Node and LiveKit using systemd, then report real readiness. The exact secure first-use/passphrase, TLS, account authentication and initial-key-exchange design remains unconfirmed.
8. Store the provider resource IDs and states; retry idempotently, reconcile uncertain responses against provider resources before re-creating, and alert on partial failure. On reboot the locked-page service must start without the volume and notify the owner; application services must wait for the mount. Back up encrypted data independently and test restoring to a fresh VM and changing DNS.

DNS can be on the same provider or on an independent authoritative DNS API; using a DNS-only provider does not place the media connection through that provider. I did **not** verify a current free API tier for deSEC, Porkbun, Namecheap, or Route 53, so do not assume one.

## 3. What a call needs

A selective forwarding unit (SFU) forwards each participant's media to others rather than mixing or decoding the media. LiveKit's [benchmark](https://docs.livekit.io/transport/self-hosting/benchmark/) says work depends on number of tracks, subscribers, data and packet rates; transport encryption/decryption and packet forwarding still cost CPU. [LiveKit E2EE docs](https://docs.livekit.io/transport/encryption/) say media content stays encrypted to endpoints when enabled. Its benchmark on a 16-core compute-optimized Google VM reports 150 publishers/150 subscribers at 720p, 50 MB/s in and 93 MB/s out, at 85% CPU; its audio-only test assumes only 3 kbps per stream and reports 10 publishers/3,000 subscribers, so neither is a direct benchmark of Scry or proof that every video is sent to every viewer.

**Illustrative engineering assumptions, not Scry measurements:** each voice stream is continuously 32 kbit/s, each selected video layer 1 Mbit/s, and each screen share 2 Mbit/s. All other participants receive every stream, with no simulcast savings, silence suppression, packet overhead, TURN retransmission, other traffic, or headroom. Inbound = senders × bitrate; outbound = directed sender/viewer pairs × bitrate. Decimal GB/hour = outbound Mbps × 0.45. Group membership is not simultaneous attendance.

| Scenario | Inbound | Outbound | Outbound per hour |
|---|---:|---:|---:|
| 10 simultaneous voices | 0.32 Mbps | 2.88 Mbps | 1.296 GB |
| 10 people each publish video to 9 others | 10 Mbps | 90 Mbps | 40.5 GB, plus voice |
| 25 simultaneous voices | 0.8 Mbps | 19.2 Mbps | 8.64 GB |
| One screen shared to 10 distinct viewers | 2 Mbps | 20 Mbps | 9 GB, plus voice |

At those assumptions, a 10-person video night lasting 3 hours every day is roughly 3.65 TB outbound in a 30-day month, before voice, overhead or retransmissions: this can exhaust small plans. Real UI behavior, simulcast layers, bitrate, active speaker selection, 720p/1080p, simultaneous calls, TURN percentage, CPU contention, packet loss and data growth change the answer materially. [LiveKit's simulcast docs](https://docs.livekit.io/transport/media/advanced/) explain different layers may be sent to different viewers. The 2-vCPU/2-GiB starting recommendation is a **load-test hypothesis**, not a 50-user guarantee. Next: test the same 2-vCPU/4-GiB machine; if forwarding is CPU-bound, upgrade CPU rather than RAM. Use [LiveKit's test tools and benchmark](https://docs.livekit.io/transport/self-hosting/benchmark/), realistic Scry clients and monitoring for CPU steal, memory, packet loss, jitter, relay traffic and actual invoice egress. Test a real reboot/unlock and restore too.

## 4. Resale and terms

These are source readings, not legal advice. A hosted application and direct resale of a VM are not necessarily legally identical; describe the exact Scry business model to each provider and get confirmation before launch.

* **DigitalOcean:** [partner terms §1.1–1.2](https://www.digitalocean.com/legal/partner-terms-and-conditions) authorize approved channel and ISV tracks; the ISV track explicitly covers reselling services as part of the partner's own product. The terms require acceptance and provide end-customer obligations; ask whether Scry must enroll and what end-user terms must be passed through. Team isolation does not automatically equal a legally independent account.
* **Vultr:** [terms §12.2](https://www.vultr.com/legal/tos/) expressly contemplate customers acting as service providers, including hosting/reselling bandwidth, with content obligations. But [partner program §2.1](https://www.vultr.com/legal/partner-program/) says program acceptance alone does **not** authorize resale/sublicensing. Resolve the difference and obtain written permission for the actual model.
* **Hetzner:** [general terms §7.1](https://www.hetzner.com/legal/terms-and-conditions) say the customer may grant third parties use of ordered services and remains the sole contractual party and liable. Check applicability to the specific cloud contract and whether further terms apply.
* **Contabo:** its [API page](https://contabo.com/en-us/contabo-api/) explicitly markets provisioning to SaaS and resellers. That is not a reviewed contractual clause; formal terms and any specific resale restrictions remain unconfirmed.
* **Akamai/Linode, OVHcloud, Scaleway, Lightsail, Netcup, Hostinger:** contractual permission, partner discounts, end-customer obligations and customer-per-project isolation **unconfirmed**. No outright prohibition was established from sources checked; that is not proof of permission. Ask all before selling.

| **Northflank** | [Public networking](https://northflank.com/docs/v1/application/network/networking-on-northflank) terminates HTTPS at an edge load balancer; ordinary public service ports are HTTP, while TCP/UDP are internal. Not this direct UDP VM. |
| **Railway** | [Volumes](https://docs.railway.com/volumes/reference) persist with a service, but its product model is not established as a raw public VM with a LUKS block device and direct UDP. Not established fit. |
| **Render** | [Persistent disks](https://render.com/docs/disks) are mounted into a service, encrypted by Render, and the rest of the filesystem is ephemeral; raw customer-LUKS disk and direct UDP VM unconfirmed. Not established fit. |
| **Cloudflare Sandboxes/Containers** | [Lifecycle](https://developers.cloudflare.com/sandbox/concepts/lifetime/) is Worker/Durable Object controlled and an instance can stop without guaranteed duration; files/processes end with it absent a snapshot. Cloudflare intermediary is disqualifying under this brief. |
| **Vercel Sandbox** | [Persistent sandbox](https://vercel.com/docs/sandbox/concepts/persistent-sandboxes) means snapshots across separate VM sessions, not necessarily an uninterrupted server; direct UDP/raw disk unconfirmed. |
| **Runloop** | [Devbox](https://docs.runloop.ai/docs/devboxes/start-stop) default max lifetime is one hour, configurable; direct public UDP/raw disk and indefinite setup unconfirmed. |
| **Morph** | [Docs](https://cloud.morph.so/docs/devboxes/prototyping) explicitly offer an always-on full VM with auto-sleep/TTL off, but expose an HTTP preview; direct public UDP/raw block device and the traffic path remain unconfirmed. Strongest sandbox lead to ask, not a current recommendation. |
| **Blaxel** | [Docs](https://docs.blaxel.ai/Sandboxes/Overview) describe automatic standby and restored memory, with lost external network connections; keep-alives can prevent standby. Public UDP/raw-disk and direct IP unconfirmed. |
| **Coder** | [Self-hosted control plane](https://coder.com/docs/admin/infrastructure) can provision workspaces on VMs or pods; unlike an agent-sandbox cloud it may manage infrastructure one already owns. Not shown to supply Scry billing or the exact encrypted-disk/direct-UDP workflow; extra control-plane complexity. |

## 6. Home box: a useful second door, not a shortcut

A Raspberry Pi 5 or x86 mini-PC with an NVMe SSD could run the same systemd-based Scry installer in a customer's closet, but the total hardware cost must include power supply, case/cooling, NVMe adapter and SSD; a current complete-kit price is **unconfirmed**. Raspberry Pi's [April 2026 price notice](https://www.raspberrypi.com/news/a-new-3gb-raspberry-pi-4-for-83-75-and-more-memory-driven-price-increases/) says the 1–2 GB Pi 4/5 variants were in the $35–$65 range and documents subsequent memory-related increases for larger models; don't use that range as a quote for a 4-GB kit. LiveKit publishes a [Linux ARM64 release](https://github.com/livekit/livekit/releases/tag/v1.13.3). A ten-person Pi call is **unverified**; benchmark the complete Scry stack, thermal throttling, disk and home upload, not merely whether the binary starts.

Home routers translate private addresses (NAT), so reaching a server usually needs port forwarding and a reachable public address; carrier-grade NAT can prevent ordinary inbound forwarding. An independently hosted TURN relay can forward encrypted media packets without decoding end-to-end-encrypted content, but it is a third-party traffic path unless it is owned/operated as part of the product, and creates egress cost and an extra operational dependency. A relay does not solve the home box's upload limit. Test client connectivity, network changes, dynamic IP, power loss and manual unlock; neither Pi capacity nor a no-relay experience is promised.

## 7. Gotchas to take into the call

* **Fraud and abuse:** a stolen card can turn into paid outbound bandwidth and abuse on infrastructure Scry owns. Limit new accounts and provision rates, use payment/fraud signals, watch outbound traffic and complaints, and define a human-reviewed suspension path. End-to-end encryption does not remove the hosting provider's abuse obligations.
* **Quotas are not throughput:** DigitalOcean's [limits](https://docs.digitalocean.com/products/droplets/details/limits/) say no more than 10 Droplets can be created *simultaneously* in a request/operation; that is not a proven account-wide default cap. Ask for total account capacity and increases before a launch. Akamai's [block-storage docs](https://techdocs.akamai.com/cloud-computing/docs/block-storage) list 250 volumes per account by default and tell users to request a higher quota. One disk per group reaches that limit quickly.
* **Snapshot != backup:** a live filesystem image may not be database-consistent; use a Postgres-consistent backup and verify restic restore. DigitalOcean, Vultr, and Hetzner exclude attached volumes from their instance backups/snapshots, with varying support for separately snapshotting volumes ([DO](https://docs.digitalocean.com/products/snapshots/details/limits/), [Vultr](https://docs.vultr.com/product-overviews/backups), [Hetzner](https://docs.hetzner.com/cloud/volumes/overview/)). An encrypted backup is unusable if the customer loses the passphrase and the design intentionally retains no recovery key.
* **Cancellation:** decide and disclose the grace period, locked-state access/export, backup retention, deletion deadline, and final deletion of VM, disk, DNS, snapshots and backup objects. Destroying a VM may not stop charges for its detached disk; DigitalOcean explicitly bills detached [volumes](https://docs.digitalocean.com/products/volumes/details/pricing/). Keep per-resource IDs and reconcile actual deletion.
* **Pricing and IP addresses:** public IPv4 is scarce and terms differ; some plans bundle it and others charge it separately. Plan for both direct IPv4 and IPv6, but do not assume IPv6-only reaches all clients. Usage caps, alerts and customer disclosure matter more than the headline machine price; pooled allowances can mask a heavy user.
* **Residency and operator access:** let customers choose a region and explain backup location, control-plane metadata and support access. A provider's virtual machine isolation is not protection from the host while the machine is unlocked. An offsite encrypted backup is not a traffic proxy, but still uses another storage service and its location/keys must be explicit.
* **A builder's real-world example:** [KiwiClaw's account of one Fly VM per customer](https://kiwiclaw.app/blog/multi-tenant-isolation-fly-io/) says injected files were hidden by a later volume mount, and that its boot/resume flow must account for ephemeral root filesystems and idempotent cleanup. Its Fly edge terminates TLS and forwards traffic, so its architecture is **not** a template for Scry's no-intermediary requirement. These are the operator's claims, not independently reproduced here.
* **Owner availability after reboot:** a box may boot locked while nobody is awake; users cannot call until an owner unlocks. Monitoring must distinguish healthy-but-locked from a dead VM. Automated updates, snapshots and resizes must not silently break the locked-page service.
